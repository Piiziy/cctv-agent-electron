# 실시간 무인매장 CCTV 이상행동 감지 — 영상 수집 에이전트 설계

작성일: 2026-09-07

## 1. 배경

전체 시스템은 다음과 같다.

```
[CCTV] → [수집 에이전트] → [백엔드] → [AI(LLM) 서버] → 위험도 산출
                                │
                                └─ 위험도 임계 초과 → [프론트 표시 + 앱 푸시알림]
```

이 문서는 **수집 에이전트**만 다룬다. 백엔드·AI 서버·프론트·모바일 앱은 범위 밖이며,
백엔드와의 계약(API 규격)만 여기서 정의한다.

### 최우선 제약

개발과 테스트는 웹캠·테스트 영상으로 하지만, **실제 CCTV로 교체했을 때 에이전트가
아무 수정 없이 동작해야 한다.** 이 제약이 이후 모든 설계 결정의 기준이다.

이를 보장하는 방법은 하나뿐이다 — **에이전트는 오직 RTSP로만 영상을 받는다.**
웹캠을 직접 읽는 지름길을 만들지 않는다. 웹캠 테스트조차
`웹캠 → 가짜 카메라(RTSP 서버) → 에이전트` 경로를 거친다.
지름길을 하나라도 뚫는 순간 교체 보증이 깨진다.

## 2. 범위

### 포함

- Electron 데스크톱 앱 (매장 PC에 설치)
- ONVIF 카메라 자동 검색 및 선택 (+ RTSP 주소 수동 입력)
- RTSP 수집 → 5분 단위 조각 생성 → 백엔드 업로드
- 자동 복구 (카메라 끊김·프로세스 사망), 오프라인 중 디스크 보관
- 백엔드 API 규격 정의

### 제외

| 제외 항목 | 사유 |
|---|---|
| 백엔드 서버 구현 | 미개발. 이 문서에서 규격만 정의 |
| AI/LLM 분석, 프론트, 모바일 앱, 푸시 | 다른 산출물 |
| 모니터 없는 매장 지원 (QR 페어링·소프트AP·백엔드 명령중계) | 대상 매장을 "모니터 있는 매장"으로 한정 |
| ~~카메라 다중 동시 수집~~ | **2026-09-08 구현됨.** 아래 "여러 대 수집" 참조 |

### 전제

- 매장 PC에 모니터가 있고, 사람이 화면 앞에서 설정한다
- 카메라와 PC가 같은 네트워크(L2)에 있다
- 인터넷 연결이 있다 (일시적 끊김은 견딘다)
- 카메라가 ONVIF Profile S/T 호환이다 (아니면 RTSP 주소 수동 입력으로 우회)

## 3. 프로토콜 조사 결과

CCTV는 단일 프로토콜이 아니라 3개 층으로 나뉜다.

### 3.1 디바이스 발견·제어 — ONVIF

IP 카메라 업계 표준. SOAP/XML over HTTP.

| Profile | 역할 | 상태 |
|---|---|---|
| S | 기본 스트리밍(H.264) + PTZ | 2025-10-09 종료 발표. 2027-03-31 이후 신규 인증 불가 |
| **T** | S의 후계. H.264 + H.265, 다중 스트림, 모션·탬퍼 이벤트 | 현재 표준 |
| M | 분석 메타데이터·이벤트 (SOAP pull-point + MQTT/JSON) | 향후 위험도 결과 반환에 적합 |
| G | 엣지 녹화·재생 | 참고 |

- **WS-Discovery**: UDP multicast `239.255.255.250:3702` 로 탐색 요청을 뿌리면
  카메라가 자기 ONVIF 서비스 주소(XAddr)로 응답한다. 프린터 자동 검색과 같은 원리.
- `GetProfiles` → 프로필별 해상도·코덱·비트레이트
- `GetStreamUri(profile, RTSP)` → 실제 RTSP URL
- ONVIF 자체는 영상을 나르지 않는다. "어디로 가면 영상이 있는지"만 알려준다.
- NTP 시각 동기가 규격상 필수 항목이다.

### 3.2 미디어 전송 — RTSP/RTP (사실상 유일한 표준)

- **RTSP** (RFC 2326 / 7826), TCP **554**. `DESCRIBE → SETUP → PLAY → TEARDOWN`.
  SDP로 코덱 협상, Digest 인증.
- 영상 본체는 **RTP**로 전달. UDP 짝수 포트 + RTCP 홀수 포트,
  또는 **RTP over TCP interleaved** (RFC 2326 §10.12).
  매장의 NAT·방화벽 환경에서는 **TCP interleaved가 실무 기본값**이다.
- 페이로드 포맷: H.264 → RFC 6184, H.265 → RFC 7798

**RTSP는 pull 모델이다.** 카메라가 서버로 앉아있고 클라이언트가 접속해서 당겨간다.
카메라가 백엔드로 밀어넣지 않는다. 따라서 "CCTV가 백엔드로 영상을 보낸다"는 동작은
표준 CCTV에 존재하지 않으며, 당겨오는 주체(= 수집 에이전트)가 반드시 필요하다.

### 3.3 push 계열 (참고)

`RTMP`(TCP 1935, 레거시) · `SRT`(UDP, 손실 네트워크 대응) · `WebRTC/WHIP`(저지연) ·
`GB/T 28181`(중국 국가표준, SIP 기반 — 국내 무관) · `MQTT`(영상 아님, 이벤트용).

표준 IP 카메라 대부분이 push를 지원하지 않으므로 채택하지 않는다.

### 3.4 메인스트림 / 서브스트림

거의 모든 IP 카메라가 스트림을 2개 이상 동시에 낸다.

| | 용도 | 전형적 사양 | 5분 조각 크기 |
|---|---|---|---|
| 메인스트림 | 녹화(NVR) | 1920×1080, 4 Mbps | 약 150 MB |
| **서브스트림** | 실시간 미리보기·분석 | 704×480, 512 kbps | **약 19 MB** |

무인매장 인터넷은 업로드가 느린 비대칭 회선이다. 메인스트림을 상시 업로드하면
매장 회선을 통째로 점유한다. **AI 분석에는 서브스트림으로 충분한 경우가 많으므로
기본값을 서브스트림으로 하고, 사용자가 선택할 수 있게 한다.**

### 3.5 조각내기(세그먼트)의 제약

카메라는 연속 스트림만 낸다. 자르는 것은 받는 쪽의 일이다.
**H.264/H.265는 IDR 프레임(GOP) 경계에서만 잘라야 디코딩이 된다.**
임의 지점에서 자르면 재생 불가능한 조각이 만들어진다.

### 3.6 설치 현장

- CCTV 배선의 실무 표준은 **유선 PoE**다. 랜선 하나로 전원+데이터를 함께 보낸다.
  무선 CCTV는 안정성 문제로 기피된다.
- 표준 구성: `카메라 N대 → NVR → 공유기 → 인터넷`
- **인터넷 회선은 사실상 100% 있다** (무인결제가 사업의 전제).
  **와이파이(무선)는 보장되지 않는다** — 유선 전용이거나, 손님용 와이파이만 있고
  내부망과 VLAN 분리된 경우가 있다. 이 문서의 범위(모니터 있는 매장)에서는
  PC가 유선으로 같은 망에 있으므로 무관하다.
- 기존 CCTV는 건드리지 않는다. 에이전트가 도는 PC는 **공유기에 붙을 뿐**이며,
  IP 카메라는 동시 다중 클라이언트 스트리밍을 지원하므로
  NVR은 메인스트림으로 계속 녹화하고 에이전트는 서브스트림을 따로 받아간다.

## 4. 아키텍처

```
Electron 메인 프로세스 (Node)
  ├─ DiscoveryService   ONVIF WS-Discovery → 카메라 목록
  ├─ CameraProbe        ONVIF 인증 → RTSP URL·해상도·코덱·프로필
  ├─ SnapshotService    ffmpeg 1프레임 추출 → 미리보기 이미지
  ├─ SegmentRecorder    ffmpeg 자식 프로세스 → 5분 mp4 조각 생성
  ├─ SpoolStore         조각 파일 큐 관리 (디스크)
  ├─ Uploader           HTTPS multipart 업로드 + 재시도
  ├─ Supervisor         프로세스 감시·재시작·상태 집계
  └─ ConfigStore        설정 영속화

렌더러 프로세스 (React)
  └─ 화면 3개: 카메라 선택 / 카메라 설정 / 대시보드
```

### 데이터 흐름

```
[카메라] ─RTSP/TCP─> ffmpeg ─5분 mp4─> spool/ ─> Uploader ─HTTPS─> [백엔드]
                        │                 │           │
                     사망 감지        상한 초과시    성공시
                        │            오래된것 삭제   파일 삭제
                    Supervisor ──────────> 화면 상태
```

### 격리 원칙

각 구성요소는 하나의 책임만 지고 서로 독립적으로 동작한다.

- `SegmentRecorder`가 죽어도 `Uploader`는 쌓인 조각을 계속 올린다
- `Uploader`가 막혀도 녹화는 계속된다 (조각이 디스크에 쌓일 뿐)
- 각각 따로 테스트할 수 있다

## 5. 구성요소 상세

### 5.1 DiscoveryService

- `onvif` npm 패키지의 `Discovery.probe()` 사용 (WS-Discovery)
- 타임아웃 5초, 응답을 XAddr 기준으로 중복 제거
- 결과: `{ xaddr, name, manufacturer, model, ip }[]`
- **검색에 안 잡히는 카메라를 위한 수동 입력 경로는 필수다.**
  ONVIF가 꺼져있거나 다른 서브넷에 있는 카메라가 반드시 나온다.

### 5.2 CameraProbe

- ONVIF 인증(Digest) 후 `GetProfiles` → `GetStreamUri`
- 프로필을 해상도 기준으로 정렬해 메인/서브를 판정한다
- 인증 실패 시 **제조사별 구체적 안내**를 노출한다.
  (일부 제조사는 관리자 계정과 별개로 ONVIF 전용 계정을 만들어야 한다.
  단순히 "비밀번호가 틀렸습니다"로 끝내면 사용자가 막힌다.)

### 5.3 SnapshotService

브라우저·Electron 렌더러는 RTSP를 재생할 수 없다.
따라서 미리보기는 **스냅샷 이미지를 주기적으로 갈아끼우는 방식**으로 한다.

```bash
ffmpeg -rtsp_transport tcp -i <rtsp> -frames:v 1 -f image2 -y <out.jpg>
```

갱신 주기 2초. "이 카메라가 계산대가 맞는가"를 확인하는 용도로 충분하다.

### 5.4 SegmentRecorder (핵심)

```bash
ffmpeg -rtsp_transport tcp -i <rtsp> -an -c:v copy \
       -f segment -segment_time 300 -reset_timestamps 1 \
       -segment_format mp4 -strftime 1 \
       -segment_list <spool>/manifest.txt -segment_list_type flat \
       <spool>/seg_%Y%m%d_%H%M%S.mp4
```

| 옵션 | 이유 |
|---|---|
| `-rtsp_transport tcp` | NAT·방화벽 환경의 실무 기본값 |
| `-c:v copy` | **재인코딩 없음.** CPU 거의 미사용, 화질 손실 0 |
| `-an` | CCTV 오디오는 이번 범위에서 불필요 (설정으로 뺀다) |
| `-f segment` | **키프레임(IDR) 경계에서만 자른다.** GOP 제약이 자동 해결됨 |
| `-segment_time 300` | 5분. 설정값 |
| `-strftime 1` | 파일명에 벽시계 시각을 기록 (시각 추적의 근거) |
| `-segment_list` | **조각 완성 신호.** 아래 참조 |

**`-segment_list`가 필수인 이유**: `-f segment`는 다음 조각이 시작되어야 이전 조각을
닫는다. 디렉토리만 감시해서 파일이 보이자마자 업로드하면 **아직 다 쓰이지 않은 파일을
올리게 된다.** manifest 파일에 한 줄이 추가되는 시점이 그 조각이 완성된 시점이다.

**RTSP 타임아웃 옵션**: 응답이 끊긴 카메라에 ffmpeg가 무한 대기하지 않도록 타임아웃을
건다. 옵션명이 ffmpeg 버전에 따라 다르므로(`-stimeout` / `-timeout` / `-rw_timeout`)
번들할 `ffmpeg-static` 버전에서 실제로 동작하는 것을 확인하고 확정한다.
어느 쪽이든 `Supervisor`의 무진행 감지(5.7)가 2차 방어선으로 동작한다.

**컨테이너**: mp4를 기본으로 한다. 조각마다 파일이 정상 종료되므로 moov atom 문제가
없다. mp4에서 문제가 생기면 MPEG-TS(`-segment_format mpegts`)로 대체 가능하다.

### 5.5 SpoolStore

- 위치: `app.getPath('userData')/spool/`
- 파일 존재 = 미업로드. 업로드 성공 시 삭제
- 상한 기본값 **5 GiB** (서브스트림 5분 조각 ≈ 19MB → 약 24시간치).
  메인스트림(조각당 ≈ 150MB)이면 5 GiB가 약 4시간치에 불과하다 —
  서브스트림을 권장하는 실질적 이유.
- 상한 초과 시 **오래된 조각부터** 삭제하고 화면에 경고를 남긴다

### 5.6 Uploader

- **순차 업로드(동시 1개).** 매장 업링크를 아끼기 위함
- 지수 백오프: 1s → 2s → 4s → … 최대 5분에서 고정
- 재부팅 후에는 스풀에 남은 조각부터 오래된 순으로 이어서 업로드

### 5.7 Supervisor

- ffmpeg 프로세스 사망 감지 → 백오프 재시작 (1s → 30s 상한)
- **무진행 감지**: 조각 주기(5분)의 1.5배 동안 manifest에 새 줄이 없으면
  스트림이 멈춘 것으로 보고 강제 재시작
- 상태를 IPC로 렌더러에 push

## 6. 백엔드 API 규격

백엔드는 미개발이며, 이 절이 계약(contract)이다.

```http
POST {baseUrl}/v1/segments
Content-Type: multipart/form-data
Authorization: Bearer <deviceToken>
Idempotency-Key: <segmentId>

  part "meta"  : application/json
  part "video" : video/mp4
```

### meta

```jsonc
{
  "segmentId": "01K5ZQ8G3M7X2N4P6R8T0V2W4Y",  // ULID. Idempotency-Key와 동일
  "storeId": "store-gangnam-01",
  "deviceId": "agent-7f3k9m2p",
  "camera": {
    "id": "cam-01",                 // ONVIF XAddr 기반 안정 식별자. IP가 바뀌어도 유지
    "name": "계산대",                // 사용자가 입력한 이름
    "manufacturer": "Hikvision",
    "model": "DS-2CD2143G2",
    "streamProfile": "sub"          // "main" | "sub"
  },
  "video": {
    "codec": "h264",                // "h264" | "h265"
    "width": 704,
    "height": 480,
    "fps": 15,
    "durationMs": 300133,
    "sizeBytes": 19783421,
    "container": "mp4"
  },
  "startedAt": "2026-09-07T14:30:00.000Z",   // UTC (ISO 8601). NTP 동기 전제
  "endedAt":   "2026-09-07T14:35:00.133Z",
  "sequence": 1284,
  "agentVersion": "1.0.0"
}
```

### 응답별 에이전트 동작

| 응답 | 동작 |
|---|---|
| `201 Created` | 파일 삭제, 다음 조각 진행 |
| `409 Conflict` (이미 수신됨) | **성공으로 취급.** 파일 삭제 |
| `401 Unauthorized` | **재시도 중단.** 화면에 인증 실패 표시, 사용자 개입 요청 |
| `413 Payload Too Large` | 재시도 중단. "조각 길이를 줄이세요" 안내 |
| `5xx` / 네트워크 오류 | 지수 백오프 재시도 |

### 규격 설계 근거

- **`Idempotency-Key`**: 업로드는 성공했으나 응답을 받지 못하는 경우가 반드시 발생한다.
  이것이 없으면 같은 5분이 두 번 분석되어 알림이 중복 발송된다.
  `409`를 성공으로 취급하는 것도 같은 이유다.
- **`sequence`**: 백엔드가 누락을 감지하는 용도. 1283 다음에 1285가 오면 하나 빠진 것이다.
  **`(deviceId, camera.id)` 조합마다 독립적으로 0부터 1씩 증가**하며, 앱 재시작·재부팅
  후에도 이어진다(설정과 함께 영속화). 조각이 만들어진 순서를 뜻하며 업로드 순서가 아니다 —
  오프라인 보관 후 몰아서 올릴 때도 번호는 생성 시점 기준으로 유지된다.
- **ULID**: 시간순 정렬이 가능한 식별자.
- **`startedAt`/`endedAt` (UTC)**: "몇 시 몇 분에 무슨 일"을 추적하는 근거.
  ONVIF도 NTP 동기를 필수 항목으로 규정한다.
- **multipart 단일 요청**: 메타와 영상을 한 번에 보내 백엔드 파싱을 단순하게 유지.

**검토 후 배제**: S3 presigned URL 방식(백엔드 부하 감소)은 요청이 2단계가 되고
규격이 복잡해진다. 백엔드가 아직 없는 현 시점에는 과하다.
나중에 얹을 수 있는 구조는 유지한다.

## 7. 장애 처리

| 상황 | 동작 | 화면 표시 |

| 카메라 응답 없음 | ffmpeg 재시작, 백오프 1s→30s | 재연결 중 |
| 5분 주기의 1.5배 동안 새 조각 없음 | 강제 재시작 | 재연결 중 |
| 카메라 인증 실패(비번 변경 등) | **재시도 중단**, 사용자 개입 요청 | 인증 실패 |

네트워크 문제는 기다리면 해소되지만 인증 실패는 무한 재시도해도 해소되지 않는다.
후자는 즉시 중단하고 사람을 부른다.

### PC 종료 위험

모니터 있는 매장 PC는 사람이 끄거나 업데이트로 재부팅될 수 있다.

- 부팅 시 **자동 시작** 등록
- 창 닫기 = 종료가 아니라 **트레이로 최소화**
- 진짜 종료 시 "감시가 중단됩니다. 정말 종료할까요?" 확인
- (백엔드 쪽 대응 — 범위 밖 참고) "이 매장 조각이 N분째 미수신" 끊김 감지

## 8. 설정

| 항목 | 기본값 |
|---|---|
| `backendBaseUrl` | (필수 입력) |
| `deviceToken` | (필수 입력) |
| `storeId` | (필수 입력) |
| `deviceId` | 최초 실행 시 자동 생성 후 영속화 (사용자 편집 불가) |

| `streamProfile` | `sub` |
| `spoolLimitBytes` | `5 GiB` |

**`segmentSeconds`를 설정값으로 두는 이유**: 5분 조각은 이상행동 알림이 최대 5분 지연된다.
절도 행위는 통상 30초 내에 종료되므로 알림 시점에는 이미 상황이 끝나 있다.
반대로 배회처럼 느린 행동은 긴 맥락이 유리하다.
운영하며 조정할 값이므로 코드 변경 없이 바꿀 수 있어야 한다.

## 11. 테스트 전략

### 가짜 카메라 (테스트 도구)

카메라 검색을 실제로 검증하려면 응답할 카메라가 필요하다. 실물 카메라가 없으므로
최소한의 가짜 카메라를 만든다. **산출물이 아니라 테스트 도구다.**

- MediaMTX + ffmpeg로 mp4/웹캠을 RTSP로 노출 (메인·서브 2개 스트림)
- WS-Discovery 요청에 응답하고 `GetProfiles`/`GetStreamUri`를 처리하는 최소 ONVIF 응답기

### 검증 항목

| 대상 | 방법 |
|---|---|
| 조각 유효성 | `ffprobe`로 키프레임 시작 여부·길이·코덱 확인 |
| 업로드 규격 | 요청을 받아 검사만 하는 테스트용 수신 서버 (테스트 픽스처) |

| 오프라인 보관 | 수신 서버를 죽인 뒤 조각이 축적되고, 복구 시 순서대로 전송되는지 |
| 스풀 상한 | 상한 초과 시 오래된 것부터 삭제되는지 |

## 11.5 여러 대 수집 (2026-09-08 추가)

`Supervisor` 하나가 카메라 하나를 맡던 구조를 둘로 나눴다.

| | 책임 |
|---|---|
| `CameraWorker` | 카메라 한 대의 녹화·재접속·조각 축출. 카메라 수만큼 존재 |
| `Fleet` | 워커들을 띄우고, **업로더 하나**를 카메라 간 라운드로빈으로 굴린다 |

**업로드를 워커가 직접 하지 않는 이유**: 카메라마다 올리면 대수만큼 동시 업로드가
일어나 매장 업링크를 다 먹는다. 조각을 스풀에 놓는 데까지만 워커가 하고,
보내는 일은 Fleet 하나가 순서대로 맡는다. 마지막에 올린 카메라의 다음 순서부터
훑어 한 카메라가 밀려도 다른 카메라가 굶지 않는다.

**조각 경계를 벽시계에 맞춘다**(`-segment_atclocktime 1`). 카메라마다 시작 시각이
달라도 14:30, 14:35처럼 같은 시각에 잘린다. 무인매장 이상행동은 한 카메라로 판단이
안 되는 경우가 많아, AI 서버가 같은 구간의 여러 카메라를 나란히 볼 수 있어야 한다.

**보관 공간은 총량을 카메라 수로 나눈다.** 한 카메라가 공간을 다 먹어 다른 카메라
영상을 밀어내는 일을 막는다. 카메라별 폴더 이름은 카메라 id 의 해시다 —
`urn:uuid:…` 나 RTSP 주소를 그대로 폴더명으로 쓰면 윈도우에서 만들어지지 않는다.

**설정 마이그레이션**: 기존 `selectedCamera`(단수)는 읽을 때 `cameras` 배열로 옮긴다.
없으면 기존 사용자가 업데이트한 뒤 카메라를 다시 골라야 한다.

**API 규격은 바뀌지 않았다.** `camera.id` 로 구분되고 `sequence` 는 이미
`(deviceId, camera.id)` 별 카운터였다.
