# 데모가 최종적으로 가야 할 곳

2026-09-18 결정. 심사위원이 웹에서 체험하되, **흐름은 실제 서비스 그대로** 돌린다.

## 목표 흐름

```
특별 URL 로 접속
   ↓
그 URL 에 묶인 특정 계정으로 자동 로그인 (PC · 모바일 둘 다)
   ↓
데모 영상을 CCTV 인 척 연결하는 플로우
   ↓
5분 단위로 잘라 실제 서버로 전송
   ↓
백엔드에서 AI 가 분석
   ↓
AI 가 위험으로 판단하면 → 그 계정의 모바일로 푸시 알림
```

핵심은 **AI 판정이 진짜여야 한다**는 것이다. 지금 데모는 "이 구간이 위험하다"를 화면이
지어내지만, 목표 구조에서는 백엔드의 AI 워커가 실제로 판단한 결과만 알림이 된다.

## 지금과 무엇이 다른가

| | 지금 (`feat/web-demo` → main) | 목표 |
|---|---|---|
| 로그인 | 데모 모드가 가짜 세션을 끼움 | 특별 URL 의 토큰으로 **실제 계정** 로그인 |
| 데이터 | 브라우저 안의 가짜 서버 | **배포된 백엔드** |
| 영상 수집 | 화면이 재생만 함 | 데모 영상을 RTSP 로 물려 **실제로 5분씩 잘라 업로드** |
| 위험 판정 | 화면이 정해진 시각에 지어냄 | **AI 워커의 실제 판정** |
| 푸시 | 데스크톱이 직접 발송 | 백엔드가 AI 결과를 보고 발송 |

## 미해결 — 가장 큰 구멍

**웹 브라우저는 RTSP 를 못 연다.** "데모 영상을 CCTV 인 척 물려 5분씩 잘라 올린다"는
데스크톱 앱이 하는 일이고, 그래서 이 제품이 Electron 인 것이다. 심사위원이 브라우저만
여는 상황에서 이 구간을 어떻게 진짜로 돌릴지는 아직 답이 없다. 후보는 셋이다.

1. **서버 쪽에서 돌린다** — 데모 계정에 붙은 수집기를 우리 서버에서 상시 가동해 놓고,
   심사위원은 그 결과를 보기만 한다. 업로드·분석·푸시는 전부 진짜다.
   대신 "심사위원이 영상을 넣는" 조작감은 없다.
2. **심사위원이 데스크톱 앱을 깐다** — 규정상 설치 파일 직접 배포가 금지라 불가.
3. **지금처럼 화면만 흉내** — 가장 안전하지만 AI 판정이 진짜가 아니다.

1번이 유력하다. 목표 흐름의 "실제 AI 판정 → 실제 푸시"를 지키면서 브라우저 제약도 피한다.

## 현재 배포

Vercel · `main` 푸시마다 자동. 루트 `vercel.json` 이 빌드 명령과 출력 폴더를 갖고 있고,
Import 할 때 Root Directory 만 비워 두면 된다.
